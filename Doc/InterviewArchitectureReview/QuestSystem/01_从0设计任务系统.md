## 1. 需求(Requirements)

### 该问自己什么问题?

> "一个最传统的 MMO 任务系统,要解决什么**业务问题**?"

不要上来就想类。先**用业务语言**描述。

### 推导结论

一个传统 MMO 任务系统,最基本要解决这几件事:

1. **能接任务** — 玩家走到某个 NPC 那里,点一下,接取一个新任务
2. **能看任务** — 玩家能看到"自己当前有哪些任务正在进行"
3. **能完成任务** — 玩家做完任务条件(杀怪、收集、对话),任务变成"可交付"
4. **能交付任务** — 玩家回到交付 NPC 那里,点一下,获得奖励
5. **跨会话保留** — 玩家下次登录,任务状态还在
6. **NPC 头顶图标** — 玩家远远就能看到"这个 NPC 上有可接任务 / 可交付任务"

### 当前项目实现证据

| 业务能力 | 证据(代码) |
|---|---|
| 接任务 | `QuestService.OnQuestAccept` + `QuestManager.AcceptQuest`(服务端) <br/>`UIQuestDialog.OnClickAcceptButton` → `QuestManager.AcceptQuest` → `QuestService.SendQuestAccept`(客户端) |
| 看任务 | `UIQuestSystem.InitAllQuestItem` 渲染主线/支线两个列表 |
| 完成任务 | 任务状态机:`InProgress → Complated → Finished`,见 `Models/Quest.cs:22-24` 的 `CanSubmit` |
| 交付任务 | `QuestService.OnQuestSubmit` + `QuestManager.SubmitQuest` |
| 跨会话保留 | `TCharacterQuest` 表存数据库 |
| NPC 头顶图标 | `QuestManager.GetQuestStatusByNpc`(客户端)+ `UIWorldElementManager`(NPC 头顶特效) |

### [通用设计知识 — 当前项目未实现]

- 任务日志(每个玩家能浏览自己的历史任务)
- 任务追踪(右下角小地图)
- 自动接取 / 自动交付
- 任务分享(队伍成员共享同一个任务进度)

> **不要在面试里说"我做过这些"**,如果没做过。

## 2. 数据(数据建模)

### 该问自己什么问题?

> "系统要工作,**到底需要记住哪些信息**?"

关键问题:**哪些信息全服都一样**(静态配置),**哪些信息每个玩家不同**(动态数据),**哪些信息是临时算出来的**(运行时对象)。

### 2.1 静态数据(Static Configuration Data)

**通俗说**:策划填表,服务器启动时一次性加载,**永远不改**。

#### [当前项目实现]

文件:`Src/Lib/Common/Data/QuestDefine.cs`

```
任务基础信息:
- int ID                       任务唯一 ID
- string Name                  任务名
- QuestType Type               Main 主线 / Branch 支线
- string OverView              任务目标概述
- string Dialog                通用对话文案
- string DialogAccept          接受时对话
- string DialogDeny            拒绝时对话
- string DialogIncomplete      未完成催更
- string DialogFinish          交付时对话

限制:
- int LimitLevel               最低等级
- CharacterClass LimitClass    职业限制

前置:
- int PreQuest                 前置任务 ID(0 = 无前置)

NPC:
- int AcceptNPC                接取 NPC
- int SubmitNPC                交付 NPC

目标(最多 3 个):
- QuestTarget Target1/2/3      None / Kill / Item
- int Target1ID/2ID/3ID        目标 ID(怪 ID / 物品 ID)
- int Target1Num/2Num/3Num     目标数量

奖励:
- int RewardGold               金币
- int RewardExp                经验
- int RewardItem1/2/3 + Count  道具奖励
```

**专业术语**:**Game Data / Content Data / Configuration Data**

**存放位置**:`Data/QuestDefine.txt` (JSON) → `DataManager.Quests` (Dictionary<int, QuestDefine>)

**为什么用字典(而不是 List)?**
- 服务器/客户端需要按 `QuestId` O(1) 查询任务配置
- 如果用 List,接任务时要从头遍历,效率差

#### [通用设计知识 — 当前项目未实现]

- 任务类型不止 Main/Branch(没有 Daily/Weekly/Repeatable)
- 目标类型没有"对话"、"探索"、"护送"、"使用物品"
- 没有任务链(chain)概念
- 没有任务奖励池

---

### 2.2 动态数据(Dynamic / Player-specific Data)

**通俗说**:**每个玩家都不一样**,需要存到数据库里。

#### [当前项目实现]

文件:`Src/Server/GameServer/GameServer/TCharacterQuest.cs`(EF6 自动生成)

```
TCharacterQuest(每个玩家接的每一行任务):
- int Id               自增主键
- int QuestID          任务配置 ID(外键关联 QuestDefine.ID)
- int TCharacterID     玩家 ID(外键关联 TCharacter.ID)
- int Target1/2/3      目标进度(0 表示未达成)
- int Status           任务状态(0=未接?/1=完成?/2=已交付?)
```

**专业术语**:**Persistence Entity / ORM Entity**

**为什么独立成一张表(而不是塞进 TCharacter 表)?**
- 一个玩家可能有 N 个任务,1:N 关系,不能把 5 个任务的进度都塞到 TCharacter 一行里
- 任务数据稀疏(不是每个玩家都有所有任务),独立建表更省空间
- 删除/重置单个任务更容易

#### [通用设计知识 — 当前项目未实现]

- 没有 `TCharacterQuest` 的 `CreateTime`(什么时候接的)
- 没有 `CompleteTime`(什么时候完成的)
- 没有任务历史归档(交完任务就看不到记录)

### 2.3 运行时对象(Runtime Object)

**通俗说**:服务器/客户端**内存里临时使用的对象**,进程死了就没了。

#### [当前项目实现]

**客户端 `Assets/Scripts/Models/Quest.cs`**:

```csharp
public class Quest {
    public QuestDefine Define;  // 静态配置引用
    public NQuestInfo Info;     // 动态数据引用(没接取时为 null)
}
```

**服务端 `Src/Server/GameServer/GameServer/Models/Quest.cs`**:

```csharp
class Quest {
    public TCharacterQuest DbQuest;   // EF6 实体引用
    public QuestDefine Define;        // 静态配置引用
    public bool CanSubmit => IsCompleted && !IsSubmit;
    public NQuestInfo ToNQuestInfo(); // 转网络包
}
```

**核心区别**:**为什么要把"数据行"包装成"对象"**

| 维度 | 裸数据行(TCharacterQuest) | 运行时对象(Quest) |
|---|---|---|
| **生命周期** | DbContext 作用域 | 进程级 |
| **能力** | 纯字段,可读可写 | 加业务方法:`CanSubmit`、`ToNQuestInfo` |
| **持有谁** | 仅自己 | 同时持有 `Define`(配置)和 `DbQuest`(数据) |
| **写入数据库** | 通过 EF6 SaveChanges | 修改 DbQuest 后由 QuestManager 调 save |

### 2.4 五种"Quest"相关对象的对比

> 面试高频考点:**这些有什么区别?**

| 名词 | 通俗说 | 专业术语 | 在项目哪里 |
|---|---|---|---|
| `QuestDefine` | 策划写的任务表 | 静态配置 / Configuration | `Lib/Common/Data/QuestDefine.cs` |
| `TCharacterQuest` | 数据库一行任务记录 | ORM 实体 / 持久化实体 | `Server/TCharacterQuest.cs` |
| `Quest`(服务端) | 服务器内存里的"任务处理对象" | 运行时包装 / Runtime Wrapper | `Server/Models/Quest.cs` |
| `Quest`(客户端) | 客户端内存里的"任务展示对象" | 客户端 Runtime Object | `Client/Models/Quest.cs` |
| `NQuestInfo` | 网络上传输的"任务快照" | protobuf 网络包 | `Lib/proto/message.proto` |
| `NCharacterInfo` | 玩家完整数据(含任务列表) | protobuf 网络包 | 同上 |

**为什么需要这么多"Quest"?**

因为**每个角色在不同场景需要不同的视图**:
- 策划关心 QuestDefine(填表)
- DBA 关心 TCharacterQuest(建表)
- 服务器运行时用 Quest(做业务)
- 客户端展示用 Quest(显示)
- 网络传输用 NQuestInfo(序列化)

## 3. 玩家行为(Player Actions)

### 该问自己什么问题?

> "玩家**到底会对任务做什么**?每一步**谁负责**?"

### 当前项目支持的真实行为

| 行为 | 客户端做什么 | 是否请求服务器 |
|---|---|---|
| 点 NPC | `NPCManager.Interactive` → `QuestManager.OpenNpcQuest` | ❌ 仅本地查字典 |
| 打开任务面板 | `UIQuestDialog.SetQuest` | ❌ 本地数据 |
| 接取任务 | 点按钮 → `QuestManager.AcceptQuest` → `QuestService.SendQuestAccept` | ✅ 发包 |
| 交付任务 | 点按钮 → `QuestManager.SubmitQuest` → `QuestService.SendQuestSubmit` | ✅ 发包 |
| 看任务列表 | `UIQuestSystem.UIRefresh` | ❌ 本地渲染 |
| 看 NPC 头顶图标 | `UIWorldElementManager` 每帧查 `QuestManager.GetQuestStatusByNpc` | ❌ 本地查字典 |

### [当前项目未支持的行为]

- 推进任务进度(杀怪、加物品)— 没有事件总线
- 放弃任务(Abandon)— proto 里有 `QuestAbandonRequest`,但客户端没发送
- 查看任务详情(右侧详情面板)— `UIQuestInfo` 只在主线/支线列表里被使用,NPC 流程没接入

### 一次"接取任务"的完整链路(以接取为例)

```
玩家点击 NPC
 ↓
NPCManager.Interactive(npc)
 ↓
QuestManager.OpenNpcQuest(npcId)        ← 客户端本地决策
 ↓ (返回一个 Quest 对象)
触发 OnOpenQuestDialog 事件
 ↓
UIQuestDialog 打开,显示对话
 ↓
玩家点击"接取"
 ↓
UIQuestDialog.OnClickAcceptButton
 ↓
QuestManager.AcceptQuest(quest)        ← 客户端状态没变!
 ↓
QuestService.SendQuestAccept           ← 组装 QuestAcceptRequest 包
 ↓
NetClient.Instance.SendMessage         ← 发包
 ↓
(网络传输)
 ↓
服务器 QuestService.OnQuestAccept
 ↓
QuestManager.AcceptQuest(服务器端)
 ↓
DBService.Instance.save()
 ↓
拼 QuestAcceptResponse
 ↓
(网络回传)
 ↓
客户端 QuestService.OnQuestAccept
 ↓
QuestManager.OnAcceptQuest             ← 此时才更新本地 Info
 ↓
OnQuestStatusChanged 广播
 ↓
UI 刷新
```

> **关键洞察**:客户端"点接取"那一瞬间,**状态其实没变**,要等服务端回包才变。

## 4. 协议(Network Protocol)

### 该问自己什么问题?

> "任务系统**需要哪些网络包**?每个包**谁发给谁**?里面**装什么**?"

### 4.1 当前项目真实存在的协议

> 来源:`Src/Lib/proto/message.proto`

| 协议 | 方向 | 字段 | 谁发 |
|---|---|---|---|
| `QuestListRequest` | C → S | (目前未发现实质使用) | — |
| `QuestListResponse` | S → C | `result + errormsg + quests: List<NQuestInfo>` | (未发现实质使用) |
| `QuestAcceptRequest` | C → S | `quest_id` | 客户端 |
| `QuestAcceptResponse` | S → C | `result + errormsg + quest: NQuestInfo` | 服务端 |
| `QuestSubmitRequest` | C → S | `quest_id` | 客户端 |
| `QuestSubmitResponse` | S → C | `result + errormsg + quest: NQuestInfo` | 服务端 |
| `QuestAbandonRequest` | C → S | `quest_id`(存在但**客户端未使用**) | — |

> ⚠️ **重点观察**:`QuestAcceptRequest` 里**只有 `quest_id`**,**没有 `character_id`**,**没有"我要接"的标志位**。
> 这就是**服务器权威**的体现 — 客户端**不能告诉服务器"我是谁"**,服务器从 `sender.Session.Character` 拿。

### 4.2 协议设计原则(从当前项目反推)

| 原则 | 体现 |
|---|---|
| **客户端不携带身份** | QuestAcceptRequest 只有 quest_id,服务器从 session 拿角色 |
| **客户端不携带结果** | 响应里 result / quest 都是服务器权威判断 |
| **每个 Request 必须有 Response** | Success/Failed 二选一,带 errormsg |
| **Response 带回完整业务对象** | NQuestInfo 让客户端免去二次查询 |

## 5. 权威边界(Authority Boundaries)

### 该问自己什么问题?

> "**客户端可以决定什么**?什么**必须服务器说了算**?"

这是**面试中一定要说清楚**的事。

### 5.1 当前项目的权威划分

| 信息 | 客户端说了算? | 服务端说了算? |
|---|---|---|
| "我想接任务 X" | ✅ 玩家点了按钮 | — |
| "我能接任务 X 吗" | ❌(客户端可以预检,但不信任) | ✅ 服务端做最终校验 |
| "任务进度到 N 了" | ❌ | ✅(目前**没有触发流程**) |
| "任务可以交付了" | ❌ | ✅ `quest.CanSubmit` |
| "你获得 100 金币" | ❌ | ✅ `Owner.Gold += ...` |
| "任务前置完成" | ❌ | ✅ 服务端只把 Finished 状态的任务存进库 |
| "NPC 在哪 / NPC 是谁" | ✅(本地 DataManager.NPCs) | — |

### 5.2 客户端的"预检"vs 服务端的"真检"

> 这是一个常见面试题。

```
客户端预检(过滤掉明显错误,提升体验):
- 我能不能看到任务?(等级、职业、前置)
- 我能不能点接取按钮?(任务状态)

服务端真检(最终决定):
- 我到底能不能接?(服务端再用同样规则过一遍)
- 服务端不信任客户端,客户端说啥都不算数
```

**证据**:
- 客户端 `QuestManager.InitQuests` 用同样的等级/职业/前置规则过滤可接任务
- 但服务端 `QuestManager.AcceptQuest` 又做一次 `ContainsKey` 校验

### 5.3 任务进度的推进权

> ⚠️ **当前项目未完整实现**,但**设计原则**已经隐含:

```
原则:进度是"事件的结果",不是"客户端的命令"

正确:
服务端怪物死亡事件 → 服务端 QuestManager 收到通知 → 修改 DbQuest.Target1++

错误(不要这样做):
客户端: "我杀了怪,任务进度 +1"
```

**为什么?**
- 客户端可以伪造击杀
- 服务器才是"击杀事件"的发生地(因为它在管理战斗)

**当前项目状态**:
- 没有怪物死亡事件总线
- `TCharacterQuest.Target1/2/3` 字段存在,但**没有任何代码写它**
- `Models/Quest.cs:50-55` `ToNQuestInfo` 里 `Targets` 数组确实从 `DbQuest.Target1/2/3` 来

**结论**:协议层和数据结构已经**预留**了进度,业务触发逻辑**还没接**。

## 6. 客户端 / 服务端边界(Client / Server Boundary)

### 该问自己什么问题?

> "**哪些逻辑客户端做**,**哪些逻辑服务端做**?"

### 6.1 当前项目实际划分

| 职责 | 客户端 | 服务端 |
|---|---|---|
| **数据存储** | 只读配置表(DataManager) | TCharacterQuest 表 |
| **UI 显示** | ✅ | ❌ |
| **任务预检(等级/职业/前置)** | ✅ InitQuests 过滤 | ✅ AcceptQuest 校验 |
| **任务状态计算** | ❌ 不算进度 | ✅(目前没有触发器) |
| **接取 / 交付业务** | 发包 | ✅ 校验 + 改库 + 发奖 |
| **奖励发放** | ❌(显示数字) | ✅ Gold/Exp/Item |
| **NPC 头顶图标** | ✅ GetQuestStatusByNpc | ❌ |
| **数据持久化** | ❌ | ✅ DBService.save |

### 6.2 一个核心原则

> **客户端是"看"和"操作"的,服务端是"算"和"存"的。**

客户端不能信任,但可以做"看似聪明"的预检来**提升体验**。
服务端必须独立判断,不能依赖客户端发来的状态。

## 8. 同步(Synchronization)

### 该问自己什么问题?

> "客户端**怎么知道服务器上任务变了**?是**全量推**还是**增量推**?"

### 8.1 当前项目实际策略

| 阶段 | 策略 | 证据 |
|---|---|---|
| **登录** | 全量推 | `UserService.OnGameEnter` 把整个 `NCharacterInfo` 推下来,内含 `quests: List<NQuestInfo>` |
| **接取 / 交付** | 单条增量 | `QuestAcceptResponse.quest: NQuestInfo` 只回这一条 |
| **NPC 头顶图标** | 客户端本地算 | `GetQuestStatusByNpc` 直接查本地字典 |

### 8.2 为什么登录用全量,运行时用增量?

> 这是面试题。

- **登录时**:客户端啥都不知道,必须全量
- **运行时**:客户端已经知道全部状态,只需要告诉它"哪一条变了"

### 8.3 IPostResponser 钩子(服务端)

服务端有 `Character.PostResponse`,在每个 Response 拼好之后,**让 StatusManager / FriendManager 把增量塞进同一个包**。

> 当前实现:任务系统**没有**用 PostResponse 发增量。任务接取/交付的"金币变化"会走 StatusManager 的增量推送,但任务状态本身是单条 Response 自带。

```

 ↓ EF6 反序列化
TCharacter
```

```csharp
public QuestManager(Character owner) {
    this.Owner = owner;
    foreach (var dbQuest in owner.Data.Quests) {  // ← TCharacter.Quests
        Quest quest = new Quest(dbQuest);
        Quests.Add(quest.QuestId, quest);
    }
}
```

```
QuestManager.AcceptQuest
 ↓ 创建 TCharacterQuest
this.Owner.Data.Quests.Add(dbQuest)  ← 挂到 EF 跟踪列表
 ↓
DBService.Instance.save()
 ↓ SaveChanges
SQL Server TCharacterQuest 表 +1 行
```

## 10. 运行流程(完整链路)

### 该问自己什么问题?

> "把上面 9 步连起来,一个任务**从出生到死亡**长什么样?"

### 10.1 一个任务的"一生"

```
1. 策划在 QuestDefine.txt 加一条配置 → DataManager 加载到字典
2. 玩家登录 → 服务端反序列化 TCharacterQuest → QuestManager.Quests 字典
3. 玩家走近 NPC → UIWorldElementManager 查 GetQuestStatusByNpc → 显示金色感叹号
4. 玩家点 NPC → NPCManager.Interactive → QuestManager.OpenNpcQuest
5. UIQuestDialog 打开 → 玩家点接取
6. QuestAcceptRequest → QuestService.OnQuestAccept → QuestManager.AcceptQuest → save()
7. QuestAcceptResponse.quest → 客户端 QuestManager.OnAcceptQuest → allQuests.Info 赋值
8. UIQuestSystem.UIRefresh → 任务出现在"已接"列表
9. 玩家完成条件 → (目前未实现进度推进)
10. 玩家回来交任务 → QuestSubmitRequest → QuestService.OnQuestSubmit → 发奖 + status 改 Finished → save()
11. 客户端 OnSubmitQuest → InitQuests 重建 → UI 刷新

下次登录:重复 2~11
```
