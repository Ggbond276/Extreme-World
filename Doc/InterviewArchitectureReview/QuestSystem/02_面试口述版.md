## 总览(60 秒)

"我们项目的任务系统是一个比较传统的 MMO 设计,核心思路是**数据分三层**,**权限放服务端**,**协议按需增量**。

我以前会直接想 QuestManager 这个类怎么写,但实际做下来,我会先问:任务系统到底要解决什么业务问题?接任务、看任务、完成任务、交付任务、跨会话保留、NPC 头顶提示,基本就这六件事。

然后我看数据,**哪些全服一样,哪些每个玩家不同**。全服一样的就是策划配的 `QuestDefine`,存在 JSON 文件里,启动时加载到 `DataManager.Quests` 字典;每个玩家不同的就是 `TCharacterQuest` 那张表,跟玩家档案关联;还有一种是运行时临时算出来的,就是 `Quest` 运行时对象,把配置和数据包在一起,加业务方法。

后面讲网络协议、服务端权威、客户端边界,以及最终这些想法怎么落到 Service / Manager / Model 三层代码里。"

---

## 数据三层(90 秒)

"任务的数据我分了**三层**,这是我觉得这个项目里最值得讲的设计点。

**第一层静态配置**。`QuestDefine` 类,存在 `Data/QuestDefine.txt` 里,策划填的。里面有什么呢?任务 ID、名字、描述、对话文案、最低等级、职业限制、前置任务 ID、接取 NPC、交付 NPC、3 个目标的类型和数量、奖励(金币、经验、3 个道具)。这一层是**全服所有玩家共享的**,服务器和客户端都各自在启动时加载到 `DataManager.Quests` 这个字典里。注意,客户端也有 `DataManager`,跟服务端是完全相同结构,只是数据来源是 JSON。

**第二层动态数据**。`TCharacterQuest` 是 EF6 自动生成的实体,对应数据库里那张关联表。字段有 `QuestID`、`TCharacterID`、`Target1/2/3` 进度、`Status`。每个玩家接的每一个任务都是一行。注意,为什么是独立一张表而不是塞到 `TCharacter` 里?因为 1:N 关系,而且任务数据稀疏,独立建表更干净。

**第三层运行时对象**。`Quest` 类,把 `QuestDefine`(配置)和 `DbQuest`(数据行)两个引用都包在一起,再加点业务方法,比如 `CanSubmit` 判断能不能交,`ToNQuestInfo` 转成网络包。这层是进程内的,死了就没了。

面试里要是被问 QuestDefine 和 TCharacterQuest 的区别,我就直接说:**前者是策划写的,全服一样;后者是玩家做了,每人不一样**。"

## 协议设计(90 秒)

"接取任务的请求 `QuestAcceptRequest` 里**只有一个字段**,就是 `quest_id`。

这看起来很奇怪 — 玩家是谁?任务状态是什么?这些都没传。但这就是**服务器权威**的核心:**客户端不携带身份**。

服务器怎么知道是哪个玩家发的?从 `sender.Session.Character` 拿。客户端登录时,我们把账号、角色绑到 NetSession 上,后面所有请求都自动带上身份。这意味着就算客户端伪造包说自己是别的玩家,服务器也不信 — 它只认 Session 里的角色。

每个 Request 一定有 Response。`QuestAcceptResponse` 里服务器塞什么?`result` 成功还是失败,`errormsg` 失败原因,`quest` 服务器最终确认的任务状态。这个 `quest` 字段很关键 — 客户端**不能自己决定任务状态**,必须以服务器返回的为准。客户端拿到包后,把本地 `Quest.Info` 用服务器返回的覆盖,再触发 UI 刷新事件。

所以我的协议设计原则是:**客户端发'意图',服务端给'事实'**。意图是'我想接 X',事实是'你已经接了 X,状态是 InProgress'。"

## 服务器权威(90 秒)

"这一段我会专门拎出来讲,因为是面试官最爱追的。

我的项目里**任务系统有两层校验**。

**客户端预检**。在 `QuestManager.InitQuests` 里,客户端遍历所有 QuestDefine,过滤出当前玩家**可以接**的任务。规则跟服务端完全一样:等级不够踢出、职业不对踢出、前置没完成踢出、已经接了踢出。这一步的好处是**UI 体验好**,玩家看不到自己根本不能接的任务。

**服务端真检**。即使客户端校验通过,服务端 `QuestManager.AcceptQuest` 还要再校验一次 — 内存里有这个任务吗、配表里有这个任务吗。这样做的原因是:**客户端可以被改包,可以绕过预检直接发协议**。服务端不能信任客户端发来的任何'状态',只能信任客户端发的'意图'。

另外一个关键点是**任务进度的推进权**。

理想情况下,**进度应该是服务端推进的**。客户端杀怪后,应该是服务端在战斗结算时通知 QuestManager 进度 +1,而不是客户端说'我杀了一只,请你给我进度 +1'。因为客户端可以伪造击杀。

我们项目目前**没有完整实现进度推进** — `TCharacterQuest.Target1/2/3` 字段存在,proto 里也有,但**没有任何业务代码写它**。这是个**未完成的特性**,我下次迭代会接上。"

## Service vs Manager(90 秒)

"任务系统里有两层类,很多同学会搞混。我自己的理解:

**Service 是接待柜台**。`QuestService` 是单例。它在构造方法里 `Subscribe<QuestAcceptRequest>(this.OnQuestAccept)`,把自己注册到 `MessageDistributer`。它的方法签名是固定的 `OnQuestAccept(NetConnection<NetSession> sender, Request request)`,进来就 4 件事:**从 Session 拿角色,调 Manager,把结果塞 Response,SendResponse**。它不写业务,不直接改金币、不直接 save 数据库。

**Manager 是玩家管家**。`QuestManager` 是**每个角色一份**。它持有 `Owner` 引用,持有 `Dictionary<int, Quest> Quests` 这个玩家专属的任务字典。它做真正的业务 — 校验、创建 EF 实体、调 `DBService.Instance.save()`、发奖。

为啥要这么分?**职责清晰**。Service 只管网络层,Manager 只管业务层。如果以后加好友、邮件系统,新建 `FriendService` / `MailService` 都不用改 QuestService。如果要给 QuestManager 加新业务,也不用动 QuestService。

客户端这边也有同样的分层,只是 `QuestManager` 是**全局单例**(因为玩家只关心自己)。

面试题:'Service 和 Manager 区别?' 我会直接说:**Service 是'我接了你的网络请求',Manager 是'我管这个玩家的任务数据'**。"

## Session 和 Character(60 秒)

"服务器怎么知道这次请求是哪个玩家发的?

靠的是 `NetSession`。每个客户端连上来,服务器 new 一个 `NetSession`,挂到对应的 `NetConnection` 上。玩家登录时 `Session.User = user`(账号),进入游戏时 `Session.Character = character`(角色)。后面所有请求都自动带着这个 Session。

`Character` 是服务器进程内当前在线玩家的运行时实体。它里面挂着 `QuestManager`、`ItemManager`、`FriendManager` 这些 per-character 的管家。`Character.Data` 是它的 ORM 实体引用,指向数据库里那一行 `TCharacter`。

请求链路就是:**TCP 包 → NetService 收 → 找对应的 NetConnection 和 NetSession → MessageDistributer 找订阅了这种类型的 Service → Service 从 Session.Character 拿到角色 → 调角色.questManager → Manager 改 Owner.Data → save() → 回 Response**。"

## 同步策略(60 秒)

"我们项目用**混合同步策略**。

**登录时全量推**。`UserService.OnGameEnter` 拼出整个 `NCharacterInfo`,包括 `quests: List<NQuestInfo>`。客户端拿到后调 `QuestManager.Init`,清空字典,然后 `InitQuests` 重新填充 — 既包括服务器下发的已接任务,又遍历配表算出可接任务。

**运行时单条增量推**。`QuestAcceptResponse.quest` 只包含**一个** `NQuestInfo`。客户端收到后 `OnAcceptQuest(info)` 找到对应 Quest,把 Info 赋值,触发 `OnQuestStatusChanged` 事件,UI 自动刷新。

**NPC 头顶图标完全本地算**。`QuestManager.GetQuestStatusByNpc` 直接查本地字典,服务器根本不知道这件事,也不需要知道 — 这是纯展示逻辑。

为什么这样分?登录时客户端啥都不知道,必须全量;运行时客户端已经知道全局,只告诉它'哪条变了'最省带宽。NPC 图标就是本地查表,根本不该走网络。"

## 持久化(60 秒)

"任务的持久化分**读**和**写**两边。

**读**:登录时 EF6 反序列化 `TCharacter.Quests` 这个 `ICollection<TCharacterQuest>`,传给 `QuestManager` 构造函数。构造函数遍历每一行,new 一个 `Quest(dbQuest)` 包起来,塞进 `Dictionary<int, Quest>`。所以内存字典里的 Quest 都引用着 EF 跟踪的那一行。

**写**:接任务时 `QuestManager.AcceptQuest` 干四件事:
1. 校验
2. `dbQuest = Entities.CharacterQuests.Create()` 创建一个 EF 实体(还没存库)
3. `Owner.Data.Quests.Add(dbQuest)` 挂到关联表让 EF 跟踪
4. `DBService.Instance.save()` 调 `SaveChanges()`,这才真写库

**关键**:**改了内存不等于改了数据库**。中间崩溃数据就丢。我们项目目前每个事务点都立刻 save,没有事务封装,所以一致性靠'调了 save 就一定写成功'保证。

下次登录又是 EF6 反序列化,无限循环。"

## 客户端架构(60 秒)

"客户端这边架构是**View 负责画,Manager 负责算,Service 负责发**。

`UIQuestDialog` 是 NPC 对话框,只画文字、按钮、奖励图标。点接取按钮时调 `QuestManager.AcceptQuest`,然后**关面板 + 飘字**,但**不立刻改数据**。

`UIQuestSystem` 是任务列表,分主线/支线两个 ListView,有个页签切换'可接/已接'。它只**读** `QuestManager.allQuests` 字典渲染,不持有数据。

`UIQuestInfo` 是右侧详情面板,从 list 选中条目后被通知,渲染任务详情。

`QuestManager` 是客户端状态中心。三个字典:`quests`(原始列表)、`allQuests`(全 ID 索引)、`npcQuests`(按 NPC 索引)。**两个 Action 事件**:`OnOpenQuestDialog`(打开 NPC 对话框)、`OnQuestStatusChanged`(任务状态变了)。

数据来源有两边:服务器推下来的 `NQuestInfo`,本地 `DataManager.Quests` 配置表。"

## 完整性收尾(30 秒)

"总的来说,我设计任务系统的思路是:

1. **先想业务问题**,不要上来就建类
2. **数据分三层**:静态配置 / 玩家动态 / 运行时对象
3. **协议按需设计**:客户端发意图,服务端给事实
4. **服务器拥有权威**:客户端不携带身份,不决定状态
5. **Service 接待,Manager 办事**:单例 vs per-character
6. **同步分场景**:登录全量、运行时增量、UI 本地算
7. **持久化用 EF6**:读反序列化,写 SaveChanges"

## 实战提示

- **不要说"我设计了一套完美的任务系统"** — 你的项目有明确未实现的地方(进度推进、事件总线、奖励服务),主动说出来反而加分。
- **多引用类名和方法名** — 比如说 `Models/Quest.cs:24` 的 `CanSubmit`,比说"有个判断方法"专业得多。
- **承认推断** — "根据代码推断,进度推进应该是服务端事件触发的"。
- **重点演示思考路径** — 不要背答案,要背**怎么推导到答案**。
