## 1. 为什么需要 Item System

一个 MMO 玩家在游戏里会拿到、消耗、装备、出售大量物品。这些物品必须有**定义**(策划写的)、**玩家当前拥有的状态**(哪些在你背包里、有几个、装备在哪一格)、以及**跨会话的保留**(明天登录东西还在)。

这三件事合起来,需要一个独立的"道具系统"来管。否则:

- 任务奖励无处发放
- 装备没有地方存
- 买东西卖东西没有数量扣减
- 玩家上线时无法知道背包里有什么

所以 Item System 解决的根本问题是:**把"玩家拥有什么物品"这件事,从策划配置、玩家状态、跨会话保存三个角度,统一管理起来**。

证据:
- `Src/Server/GameServer/GameServer/Services/QuestService.cs` 任务完成调用 `Owner.ItemManager.AddItem(...)`
- `Src/Server/GameServer/GameServer/Managers/ShopManager.cs:28` 购买商品调用 `character.ItemManager.AddItem(...)`
- `Src/Server/GameServer/GameServer/TCharacter.cs:34` 数据库有 `Equips byte[]` 装备持久化字段
- `Src/Server/GameServer/GameServer/TCharacterItem.cs` 数据库独立道具表
- `Src/Client/Assets/Scripts/Services/UserService.cs:294-296` 登录时初始化 ItemManager / BagManager / EquipManager

证据:`Src/Lib/Common/Data/ItemDefine.cs`

| 字段 | 含义 |
|---|---|

| `Description` | 描述 |

### 2.2 玩家动态数据

**通俗说**:**"这个玩家现在拥有什么、有几个、放在哪"**。

当前项目里分两段:

#### A. 背包道具 — `TCharacterItem` 表(1:N)

文件:`Src/Server/GameServer/GameServer/TCharacterItem.cs`

```
Id          主键
ItemID      外键 → ItemDefine.ID
ItemCount   持有数量
TCharacterID 外键 → TCharacter.ID
```

**重要概念**:**这里一行就是一个"道具种类 + 总数量"**,不是"一个道具实例"。

> 比如你有 20 个血瓶 → 数据库里**只占一行**,ItemCount=20。

#### B. 装备槽位 — `TCharacter.Equips` byte[28]

文件:`Src/Server/GameServer/GameServer/TCharacter.cs:34`

```csharp
public byte[] Equips { get; set; }  // 28 字节,7 个 int 槽位
```

证据:`Src/Server/GameServer/GameServer/Services/UserService.cs:144` `Equips = new byte[28]`

每个槽位固定 4 字节(`int`),存的是 `ItemID` 或 0(空)。**装备不存数量,因为装备永远 1 件**。

#### C. 背包解锁 — `TCharacterBag`

```
Id        主键
Unlocked  已解锁格数
Items     byte[]  (当前实现:未使用,所有物品都在 TCharacterItem 表)
```

### 2.3 运行时对象

服务端 `Models/Item`:

```csharp
class Item {
    TCharacterItem dbItem;        // ← 引用 EF6 实体
    public int ItemID;            // ← 运行时缓存(避免每次查 dbItem)
    public int Count;
    public void Add(int count);   // ← 改运行时 + 同步回 dbItem
    public void Remove(int count);
}
```

客户端 `Models.Item`:

```csharp
public class Item {
    public int ItemID;
    public int Count;
    public ItemDefine define;     // ← 引用本地 ItemDefine
    public EquipDefine EquipInfo; // ← 如果是装备,引用装备配置
}
```

### 2.4 三个概念的区别(面试必问)

| 名词 | 通俗说 | 答"它是什么" |
|---|---|---|
| **ItemDefine** | 策划写的道具表 | 这个道具**本身**是什么 |
| **TCharacterItem** | 数据库一行 | 这个玩家**拥有几个**这种道具 |
| **Item 运行时对象** | 内存里的对象 | 当前这次操作**怎么改这个数据** |

面试话术:**"ItemId 是一个种类,不是一个实例。你有 20 个血瓶,这 20 个共享一个 ItemId,但运行时通过 ItemCount 区分"**。

## 4. ItemManager 为什么存在

服务端 `ItemManager` 是**每个角色一份**(per-character),挂在 `Character.ItemManager`。

文件:`Src/Server/GameServer/GameServer/Managers/ItemManager.cs`

```csharp
class ItemManager {
    public Character Owner;
    public Dictionary<int, Item> Items = new();   // ItemID → Item
    public ItemManager(Character Owner) { ... }    // 从 Owner.Data.Items 加载
}
```

**它管理什么**:

- 玩家当前**所有**道具(以 ItemID 为键的字典)
- 提供 Add / Remove / HasItem / UseItem / GetItemInfos 等业务方法
- **不**管装备槽位(那是 EquipManager)
- **不**管背包格子(服务端目前没单独的 BagManager,所有物品直接挂在 ItemManager 字典)

**为什么需要它**:
- 不可能在每次 `AddItem` 时遍历 `Character.Data.Items` 找有没有同一 ItemID — ItemManager 的字典提供 O(1) 查询
- 把"道具操作"集中在一个类里,业务逻辑不散落在 Character

**和 Character 的关系**:被 `Character` 持有(`Character.ItemManager`),生命周期随 Character。Character 销毁时 ItemManager 一起 GC。

客户端 `ItemManager` 是**全局单例**,因为客户端只关心自己一个角色。

## 5. ItemManager / BagManager / EquipManager

这是面试重点:**为什么分了三个 Manager?**

### 5.1 三个 Manager 各自的职责

| Manager | 管什么 | 数据结构 | 生命周期 |
|---|---|---|---|
| **ItemManager** | 这个玩家**拥有哪些道具,各有几个** | `Dictionary<int, Item>`(ItemID → 运行时 Item) | 服务端 per-character / 客户端全局单例 |
| **BagManager** | 这些道具**放在背包的哪些格子**(位置) | `BagItem[]`(固定大小,按索引) | 客户端**单例**(**服务端未实现独立 BagManager**) |
| **EquipManager** | **装备在哪个槽位**(头/胸/武器等) | 服务端 `byte[]` 28 字节;客户端 `Item[]` 7 长度 | 服务端**全局单例**(`EquipManager : Singleton`) / 客户端单例 |

### 5.2 三个 Manager 的关系(ASCII)

```
[服务端 Character]                    [客户端 Singleton]
    |                                       |
    +-- ItemManager                          +-- ItemManager
    |    (ItemID → Item)                     |    (ItemID → Item)
    |    拥有关系                             |    拥有关系
    |                                        |
    |  +-- TCharacter.Equips (byte[28])      +-- BagManager
    |  7 个 int,EquipManager 操作            |    (BagItem[] 位置)
    |                                        |
    |  (没有独立 BagManager)                  +-- EquipManager
    +-- 直接访问 Data.Items 表                |    (Item[7] 槽位引用)
                                             |
                                             +-- UI 只读渲染
```

### 5.3 为什么需要这三个

- **ItemManager** — 不知道"放哪个格子",只关心"我有多少个"
- **BagManager** — 知道"道具按格子摆",负责拆分堆叠、自动找空位
- **EquipManager** — 知道"装备在 7 个固定槽位里"

举例:
- 玩家买 30 个血瓶(StackLimit=99)→ ItemManager 加 1 行 Count=30;BagManager 拆分成 1 个格子 Count=30
- 玩家买 200 个血瓶 → ItemManager 加 1 行 Count=200;BagManager 拆成 3 个格子(99+99+2)
- 玩家装备武器 → EquipManager 在 byte[] 里把对应槽位写上 ItemID;ItemManager 不变

**关键设计**:
- 装备**也是**道具(ItemID),装备时 ItemManager **不增加也不删除**,只是 EquipManager 标记槽位
- BagManager 客户端特有,服务端没有 — 服务端只关心"你拥有几个",不关心格子顺序

## 6. 从玩家操作推导网络协议

### 6.1 买一个商店道具

```
玩家点击 NPC 商店
 ↓
UIShopItem(UI 层,不发包)
 ↓
玩家点"购买"
 ↓
ItemService.SendItemBuy(shopId, shopItemId)
 ↓
protobuf: ItemBuyRequest { shopId, shopItemId }
 ↓
ItemService.OnItemBuy(服务端)
 ↓
ShopManager.BuyItem(sender, shopId, shopItemId)
 ↓
character.ItemManager.AddItem(...) + character.Gold -= price
 ↓
StatusManager 记录"金币减少"和"道具增加"
 ↓
DBService.save()
 ↓
Response: ItemBuyResponse { result }
 + PostResponse: StatusNotify(同一包顺带发)
 ↓
客户端 StatusService 收到 Notify
 ↓
客户端 ItemManager.AddItem / User.Instance.AddGold
 ↓
BagManager 自动摆格子
 ↓
UI 刷新
```

### 6.2 装备一件装备

```
玩家点装备按钮(UIEquipItem)
 ↓
EquipManager.DoEquip(item)
 ↓
ItemService.SendEquipItem(item, true)
 ↓
protobuf: ItemEquipRequest { slot, itemId, isEquip }
 ↓
ItemService.OnItemEquip(服务端)
 ↓
EquipManager.Instance.EquipItem(sender, slot, itemId, true)
 ↓
验证 Items.ContainsKey(itemId)
 ↓
byte[] 对应 slot 写入 itemId
 ↓
DBService.save()
 ↓
Response: ItemEquipReponse { result }
 ↓
客户端 ItemService.OnEquipItem → EquipManager.OnEquipItem
 ↓
UI OnEquipChanged 事件触发
```

### 6.3 协议设计原则

- **请求只带意图**:客户端只发"我要做什么",不携带数量/结果
- **结果由服务器决定**:服务器自己改 db,自己回 result
- **状态变化走 Notify**:金币、道具变化通过 StatusNotify 自动跟着包一起发,不专门写 ItemNotify
- **客户端不携带身份**:`Character` 从 `sender.Session.Character` 拿

## 7. 谁拥有最终决定权

### 7.1 客户端能决定什么

- "我要买 shopItem 1001"(意图)
- "我要装备 slot 2"(意图)
- 装备 / 卸下的动画
- 背包里格子的摆放显示

### 7.2 客户端不能决定什么

- "我现在有 999 个血瓶"(状态)— 服务器不信任
- "请把我金币改成 100 万"(状态)— 服务器不信任
- "我要装备不存在于我背包的武器"— 服务器查 Items.ContainsKey 拦截

### 7.3 服务器的真检

| 操作 | 服务端校验 |
|---|---|
| 买道具 | ShopItems[shopId] 存在 + ItemCount=1 + Gold 够 |
| 装备 | `character.ItemManager.Items.ContainsKey(itemId)` |
| 增加道具 | 客户端不能触发,只能服务器自己调 AddItem(任务/商店) |

证据:
- `Src/Server/GameServer/GameServer/Managers/EquipManager.cs:19` `if (!character.ItemManager.Items.ContainsKey(itemId)) return Result.Failed;`

## 8. 客户端和服务器分别负责什么

| 职责 | 客户端 | 服务端 |
|---|---|---|
| 加载 ItemDefine 配置 | ✅ | ✅ |
| 玩家道具状态(数量) | ✅(展示) | ✅(权威) |
| 装备槽位 | ✅(展示) | ✅(权威) |
| 背包格子位置 | ✅(BagManager) | ❌(无) |
| 修改玩家道具数量 | ❌(只能等 Notify) | ✅ |
| 修改装备槽位 | ❌(只能等 Response) | ✅ |
| 发包 / 收包 | ✅(ItemService) | ✅(ItemService) |
| 数据库持久化 | ❌ | ✅(DBService) |
| 同步给客户端 | ❌ | ✅(StatusNotify + Response) |

**关键**:

- 客户端 ItemManager **只用来显示**,**永远不改自己**(改自己意味着伪造)
- 服务端 ItemManager **是真理来源**,改完会立刻 save() 和 addStatusNotify()
- `ItemService` 在两端都是**网络层入口**,只管收发包,不管业务

## 9. 数据怎么同步

### 9.1 当前项目的同步机制

**全量同步**(登录时):

```
服务端 UserService.OnGameEnter
 ↓
NCharacterInfo { Items, Bag, Equips, ... }
 ↓
客户端 UserService.OnGameEnter
 ↓
ItemManager.Instance.Init(Info.Items)
BagManager.Instance.Init(Info.Bag)
EquipManager.Instance.Init(Info.Equips)
```

**增量同步**(运行时):

```
服务端 ItemManager.AddItem / RemoveItem / Gold 变化
 ↓
StatusManager.AddItemChange / AddGoldChange
 ↓
塞进 List<NStatus>
 ↓
PostResponse(NetMessageResponse)
 ↓
Response.statusNotify.Status.Add(...)
 ↓
发包
 ↓
客户端 StatusService.OnStatusNotify
 ↓
遍历每条 NStatus
 ↓
User.Instance.AddGold / ItemManager.AddItem
```

### 9.2 关键设计

**为什么买一个道具不需要把整个背包重发?**

因为背包有 30 个格子,买一个血瓶只改了 1 行。如果每次都重发:
- 浪费带宽(30 行 × 几十字节)
- 客户端要做"全量替换"逻辑,容易出错

用 StatusNotify:**只告诉客户端"血瓶 +5"**,客户端自己合并到本地字典。

### 9.3 什么时候全量,什么时候增量

| 场景 | 策略 | 原因 |
|---|---|---|
| 登录 | 全量 | 客户端啥都不知道 |
| 玩家首次打开背包 UI | 全量 | BagManager 一次性渲染 |
| 买/用/卖 | 增量 | 客户端已知道全部状态 |
| 任务发奖 | 增量 | 跟随 PostResponse 自动推送 |

## 10. 数据怎么保存

### 10.1 内存 → 数据库

```
数据库 TCharacterItem 行
 ↓ EF6 反序列化
Character.Data.Items (ICollection<TCharacterItem>)
 ↓ ItemManager 构造函数遍历
Dictionary<int, Item> (运行时)
 ↓ 业务修改
Item.Add / Item.Remove
 ↓ dbItem.ItemCount = this.Count
TCharacterItem 字段被改(EF 跟踪)
 ↓
DBService.Instance.save()  ← SaveChanges
 ↓
SQL Server
```

### 10.2 装备槽位

```
数据库 TCharacter.Equips (byte[28])
 ↓ 直接读取
Character.Data.Equips (byte[28])
 ↓ EquipManager.UpdateEquip
fixed(byte* pt = equips) { *slotId = itemId }
 ↓
DBService.save()
 ↓
SQL Server (varbinary)
```

### 10.3 为什么不能每次都查数据库

- MMO 每个角色每秒可能多次道具操作(打怪爆装、喝药)
- 每次 SELECT 一次数据库会卡死
- 内存字典 O(1),数据库 O(磁盘 IO)
- **内存字典 + 定期 save** 是 MMO 标准做法

### 10.4 何时 save

当前实现是**每个操作立刻 save**:
- `ItemManager.AddItem` 末尾 `DBService.Instance.save()`
- `ItemManager.RemoveItem` 末尾 `DBService.Instance.save()`
- `EquipManager.EquipItem` 末尾 `DBService.Instance.save()`

生产 MMO 一般会攒批(每 30 秒 flush),当前项目简化了。

## 11. Item System 和其他系统怎么交互

### 11.1 任务系统发奖

```csharp
// 服务端 QuestManager.SubmitQuest
if (quest.Define.RewardItem1 > 0)
    this.Owner.ItemManager.AddItem(quest.Define.RewardItem1, quest.Define.RewardItem1Count);
```

**为什么任务系统调用 ItemManager 而不是自己改 DB?**

- 任务系统不应该知道"道具存在哪里、怎么持久化"
- ItemManager 暴露统一接口,业务方只管"加几个"
- ItemManager 内部负责:写 db、加 StatusNotify、save
- 跨系统调用**通过角色拥有的 manager**,不绕过

### 11.2 商店系统购买

`ShopManager.BuyItem` 也调 `character.ItemManager.AddItem`。同理,商店不直接改 db。

### 11.3 Character 是中心枢纽

```
Character
 ├── ItemManager     ← 道具(数量)
 ├── TCharacter.Equips (byte[28]) ← 装备槽位(EquipManager 操作)
 ├── questManager    ← 任务(会调 ItemManager.AddItem 发奖)
 ├── statusManager   ← 状态变化(自动加 Notify)
 └── ...
```

**为什么是 Character 持有**?

- 道具是玩家私有的,跟 Character 生命周期一致
- 玩家上线 → Character 创建 → 所有 Manager 创建
- 玩家下线 → Character 销毁 → 所有 Manager 一起 GC

## 13. 面试口述主线

> **如果面试官让我从 0 设计 Item System,我会这么说**:

---

如果让我从 0 设计一个 MMO 道具系统,**我不会先想 ItemManager 怎么写**。我会先看**业务上道具系统要解决什么问题**。

道具系统要解决三件事:**第一,策划要定义道具** — 这个道具叫什么、什么类型、能干什么、卖多少钱,这些是 ItemDefine,全服共享;**第二,玩家要拥有道具** — 玩家当前有几个血瓶、装备了哪件武器,这是玩家私有数据;**第三,要跨会话保存** — 玩家明天登录东西还在。

把这三件事分清楚,数据就分成了三层。**静态配置**放 JSON 文件,启动加载到 DataManager 字典;**玩家动态数据**放数据库,每个玩家一条记录;**运行时对象**用 Item 类把两者包起来,加业务方法。

然后我看**玩家对道具做什么**。当前项目里玩家能获得、增减数量、装备、卸下、在商店买,**没有拖拽移动、没有拆分、没有出售给 NPC**。这些是边界。

接着设计**协议**。每种玩家操作对应一个 Request。客户端发"我要做什么",**不能发"我现在有多少"**。比如买道具,客户端只发 shopId 和 shopItemId,**服务端从 Session 拿 Character,从 Character 拿 ItemManager**,自己验证、自己改 db、自己回 result。

服务端改完数据,需要**通知客户端**。我们的设计是**用 StatusNotify 这个统一的"状态变化通知"**,把金币、经验、道具变化**塞进当前响应的 statusNotify 字段**,通过 PostResponse 钩子**自动跟着主响应一起发**。这样客户端不用专门发 ItemNotify,买道具时主响应里就顺带把"+1 血瓶 -50 金币"捎过来。

模块职责分成三个 Manager:

- **ItemManager** 管"拥有关系"(ItemID → Item),不知道放哪个格子;
- **BagManager**(客户端特有)管"格子位置"(BagItem[]),知道怎么拆分堆叠;
- **EquipManager** 管"7 个装备槽位",知道武器在 Weapon 槽。

**装备也算道具**(用 ItemID 表示),**装备不消耗**,只是 EquipManager 标记槽位。ItemManager 不动。

持久化用 EF6。**内存字典是工作区,数据库是真理**。每次 AddItem / RemoveItem / EquipItem 立刻 save(),简单粗暴,生产 MMO 会攒批。

最后,**任务系统怎么发奖**?任务系统**不直接改 db**,而是调 `Owner.ItemManager.AddItem` — 跨系统调用**走角色拥有的 Manager**,不绕过。这样 ItemManager 集中负责所有"道具数量变化",任务系统不需要知道道具存在哪里、怎么持久化。
